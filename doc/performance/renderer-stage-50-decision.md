# Stage 50 Vulkan presentation-pipeline ownership decision

## Decision

Add one loader-neutral, move-only presentation-pipeline generation for the
exact Stage 48 presentation target. It owns one empty pipeline layout and one
graphics pipeline compatible with that target's render pass at subpass zero.
Shader modules exist only while the pipeline is created.

The aggregate swapchain chain now creates configuration, swapchain, image
views, presentation target, presentation pipeline, and then a fresh frame
slot. The pipeline is created and owned, but it is not bound or used by a
command buffer in this stage.

The generation remains behind the default-off Vulkan diagnostic graph. It does
not replace or modify the production OpenGL renderer. Windows remains excluded
by user direction.

## Dispatch and exact parent provenance

Resolution first authenticates the exact logical-device, configuration,
swapchain, image-view, and presentation-target generations. Invalid or stale
parents fail before dispatch lookup or native mutation.

`vkGetDeviceProcAddr`, `vkCreateShaderModule`, `vkDestroyShaderModule`,
`vkCreatePipelineLayout`, `vkDestroyPipelineLayout`,
`vkCreateGraphicsPipelines`, and `vkDestroyPipeline` resolve as one complete
candidate before the first Vulkan create call. All commands are called through
resolved function pointers under `VK_NO_PROTOTYPES`; no Vulkan loader link
dependency is introduced.

The published owner retains the exact identities and native provenance of its
five parents, including instance, surface, physical and logical device, queue
and indices, drawable extent, swapchain, image format and extent, image count,
and render pass. `createdFor()` requires both object identity and complete
retained provenance. An exact-looking but distinct presentation target is
rejected.

## Fixed pipeline and shader artifacts

The pipeline layout has no descriptor-set layouts or push-constant ranges.
Pipeline creation uses no cache, derivative, extension chain, specialization
constant, descriptor, buffer, or optional feature.

The vertex shader derives an oversized full-screen triangle solely from
`gl_VertexIndex`; it has no vertex bindings, attributes, or varyings. The
fragment shader writes fixed opaque green to location zero. These shaders
define a future diagnostic draw, but neither shader executes in this stage.

The fixed Vulkan 1.1 pipeline uses two `main` stages, triangle-list assembly,
one dynamic viewport, one dynamic scissor, fill rasterization, no culling, no
depth bias, line width one, one sample, no depth-stencil state, disabled
blending and logic operations, explicit replacement blend factors, and RGBA
writes. It avoids every relevant optional portability feature.

The checked-in GLSL sources and deterministic embedded SPIR-V are verified by
an offline regeneration script. With glslang 16.4 targeting Vulkan 1.1 and
SPIR-V Tools 1.4.357 validation, the exact artifacts are:

- vertex: 736 bytes, SHA-256
  `c22f211633f950d6f10a87934e705a32cb76f29d17b58853a5122c2a100c27c1`;
- fragment: 304 bytes, SHA-256
  `784c8df9710a1b546fa9873249b463567449f4e48b37c656c6d2ac3584e897cc`.

The verifier compares regenerated bytes with both hashes and the embedded word
arrays. It is an explicit offline check, not a runtime compiler or viewer
dependency.

## Failure handling and rollback

Every Vulkan create output starts at null. Failed single-object creation
preserves its exact result and does not interpret a poisoned output handle. A
successful call returning null has a separate typed failure.

Graphics-pipeline creation may return a non-null partial pipeline on aggregate
failure. That handle is destroyed before the fragment module, vertex module,
and layout. Other partial failures destroy only successfully created objects
in reverse dependency order. A parent change after pipeline creation rolls the
complete native child back before publication.

On success, the transient fragment and vertex shader modules are destroyed.
The owner retains only the graphics pipeline and layout. Reset destroys the
pipeline before its layout, clears every retained identity, handle, and
dispatch field, and is idempotent. Move construction transfers complete
ownership and provenance while disarming the source.

New public result and rebuild-phase values are appended so earlier ordinal
values remain stable.

## Publication, rebuild, and teardown

The instance owner validates synchronous, unretained instance and window
freshness callbacks before native acquisition. It snapshots the ownership
epoch and exact parent chain, guards the live native candidate against owner
movement and parent retirement, creates the candidate, allocates its owner,
then repeats freshness, epoch, identity, handle, format, extent, count, and
render-pass checks before atomic publication. Callback mutation, reentrant
publication, ABA replacement, allocation failure, and stale requests cannot
publish an inauthentic pipeline.

A changed-extent rebuild retires the old frame slot and pipeline before its
presentation target, then recreates target, pipeline, and a fresh frame slot.
Pipeline failure has an appended rebuild phase and rolls the partial child
chain back to reusable parents. Zero extent suspends the complete swapchain
child chain.

The lower-level frame-slot API remains independently usable without a
presentation pipeline. That is safe in Stage 50 because no frame-slot command
binds or draws with it. Pipeline reset first requires the current frame slot to
be resettable; target and parent teardown preserve all objects when an
outstanding frame obligation refuses retirement.

## Parent and platform routes

The instance generation exposes explicit pipeline acquisition, handle
inspection, reset, and aggregate rebuild ownership.

The SDL diagnostic owner samples a positive backing-pixel extent before
forwarding the authenticated request. The macOS diagnostic owner requires its
existing main-thread Cocoa identity and refreshes native geometry without
accepting an identity change. Both expose explicit diagnostic reset routes.

No production `LLWindowSDL` hook, ordinary window construction, resize event,
`swapBuffers()` path, graphics selector, viewer setting, or OpenGL ownership
changes. The macOS CGL context and global OpenGL manager remain outside the
pipeline owner.

## Evidence boundary

This stage proves that exercised Vulkan implementations accept creation,
rebuild, and destruction of the exact pipeline object graph. It does not prove
that the pipeline can complete submitted work, that either shader executes, or
that a pixel becomes green.

No pipeline bind, viewport command, scissor command, draw, readback, capture,
screenshot comparison, fixed-scene comparison, texture upload, descriptor,
material path, tonemap path, UI composition, CPU timing, GPU timing, or
performance claim enters this stage. Existing transfer and render-pass clears
used by native lifecycle tests do not bind or use the new pipeline.

## Build graph and production isolation

The pipeline library and focused test are reachable only through
`LL_VULKAN_RUNTIME_TEST` or `LL_VULKAN_TONEMAP_TEST`. SDL ownership additionally
requires `LL_VULKAN_SDL_WSI`; macOS ownership additionally requires
`LL_VULKAN_MACOS_WSI`. The GLSL files are build metadata for the diagnostic
library and add no runtime shader compilation.

Fresh all-six-off Linux and macOS builds must omit the Stage 50 source, target,
object, symbol, string, shader path, embedded SPIR-V, Vulkan create command,
import, dependency, and packaged renderer payload. Existing Chromium, SDL,
Vulkan-loader, and SwiftShader content remains accepted third-party baseline
and does not select or link the diagnostic renderer.

## Independent review

Review corrected exact GLSL-to-embedded-SPIR-V correspondence, explicit
replacement blend values, complete move/reset provenance clearing, focused
test registration, temporary-result lifetime, parent-fixture storage, and the
native SDL target-to-pipeline-to-fresh-slot ordering before source freeze.

The final macOS focused run exposed one test-fixture fallback that indexed past
its three default framebuffer handles during deliberate repeated target
creation. The corrected fixture preserves global indexing for explicit
results, cycles only its non-empty default framebuffer and shader-module
fallbacks, and passes Linux and macOS. Independent review found no adjacent
unguarded index hazard.

Final core, parent-lifecycle, platform, build-scope, and privacy review found no
remaining concrete source defect. Review verified complete pre-mutation
dispatch, Vulkan 1.1 fixed state, transient shader lifetime, aggregate partial
pipeline rollback, exact target provenance, publication freshness, rebuild and
teardown order, diagnostic-only graph placement, and Windows exclusion.

Residual risk remains in the low-level borrowed-parent and externally
serialized host-lifetime contract. The current frame slot does not authenticate
or borrow the pipeline because no Stage 50 operation uses it. Rare native
device-loss and creation-failure branches remain fake-tested because drivers
cannot reliably force them.

## Stage 51 boundary

Stage 51 may add one diagnostic draw transaction inside the exact Stage 49
render pass. It must authenticate and borrow the exact Stage 50 pipeline in the
frame-slot operation, bind it, set a full-extent dynamic viewport and scissor,
and issue one three-vertex, one-instance draw. It must preserve retry and
cancellation behavior and refuse pipeline teardown until every acquired or
submitted draw obligation is retired.

Configuration admission must additionally prove that the positive-height
viewport fits `maxViewportDimensions` and `viewportBoundsRange`; framebuffer
limits alone do not make a Stage 51 dynamic viewport valid.

The next stage still must not add readback, pixel-parity claims, performance
measurement, production renderer selection, or an OpenGL replacement.

## Explicit deferrals

- pipeline binding, dynamic viewport and scissor recording, and a draw;
- readback, capture, screenshot comparison, and fixed-scene visual parity;
- descriptors, uploads, texture sampling, materials, tonemap, and UI
  composition;
- pipeline-cache ownership and persistent shader compilation;
- surface reconstruction and complete device-loss recovery;
- multiple frames in flight and production resize, minimize, suboptimal,
  out-of-date, fullscreen, and display-change event wiring;
- memory-stability soak and measured CPU or GPU timing;
- connection to the production graphics selector or replacement of OpenGL;
- an OpenGL-to-Vulkan compatibility layer;
- Windows build and native execution;
- benchmark, image-parity, timing, or performance claims.
